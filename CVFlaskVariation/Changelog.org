** 00:25 - Fixed Voice-Activated Object Navigation Coordinate Bug
Fixed critical bug where voice-activated "find [object]" commands were setting navigation goals to incorrect locations due to coordinate transformation errors.

*** Problem
When using voice commands like "find bench" or "find door", the navigation system would set the goal to completely wrong locations on the canvas:
- Objects detected correctly with proper bounding boxes
- Voice command found the correct object
- But navigation goal was set to wrong position
- User would be directed to empty space instead of the object
- Made voice-activated navigation completely unreliable

*** Root Cause
Incorrect coordinate transformation in handleFindCommand() (main.js:224-227):
- Started with centerX, centerY in VIDEO coordinate space (e.g., 320, 240 for 640x480 video)
- Incorrectly scaled by canvas.width / videoWidth (inverse of what was needed)
- Passed result as clientX, clientY without accounting for canvas position
- setNavigationGoal() expected CLIENT coordinates (browser viewport space)
- setNavigationGoal() then converted client -> video (assumed double transformation)
- Result: goal position was completely wrong

*** Coordinate Space Confusion
Three coordinate spaces were conflated:
1. Video coordinates: [0, videoWidth] x [0, videoHeight] (e.g., 640x480)
2. Canvas coordinates: [0, canvas.width] x [0, canvas.height] (e.g., 400x300 if scaled)
3. Client coordinates: Browser viewport position (e.g., 100-500 if canvas at left=100)

Old code:
#+BEGIN_SRC javascript
// WRONG: Started in video space, scaled incorrectly, treated as client space
const syntheticEvent = {
    clientX: centerX * (detectionCanvas.width / (videoElement.videoWidth || 640)),
    clientY: centerY * (detectionCanvas.height / (videoElement.videoHeight || 480))
};
#+END_SRC

This produced coordinates in CANVAS space (0-canvas.width), but labeled them as client coordinates, causing setNavigationGoal() to misinterpret them.

*** Solution
Implemented proper three-stage coordinate transformation:
1. Start with video coordinates (from bbox)
2. Scale to canvas coordinates (multiply by canvas/video ratio)
3. Offset to client coordinates (add canvas rect.left and rect.top)

New code:
#+BEGIN_SRC javascript
// CORRECT: Proper transformation through all three coordinate spaces
const rect = detectionCanvas.getBoundingClientRect();
const scaleX = detectionCanvas.width / (videoElement.videoWidth || 640);
const scaleY = detectionCanvas.height / (videoElement.videoHeight || 480);

// Transform: video coords -> canvas coords -> client coords
const canvasX = centerX * scaleX;
const canvasY = centerY * scaleY;
const clientX = canvasX + rect.left;
const clientY = canvasY + rect.top;

const syntheticEvent = {
    clientX: clientX,
    clientY: clientY
};
#+END_SRC

*** Files Modified
- app/static/js/main.js:214-240
  - Fixed coordinate transformation in handleFindCommand()
  - Added proper video -> canvas -> client transformation
  - Added inline comments explaining coordinate spaces
  - Now correctly calculates clientX and clientY for setNavigationGoal()

*** Technical Details
Transformation mathematics:
- Video to Canvas: canvasCoord = videoCoord * (canvasSize / videoSize)
- Canvas to Client: clientCoord = canvasCoord + canvasOffset
- Combined: clientCoord = videoCoord * (canvasSize / videoSize) + canvasOffset

Example (object at video center on 640x480 video, canvas 400x300 at position 100,50):
- Video coords: centerX=320, centerY=240
- Canvas coords: 320 * (400/640) = 200, 240 * (300/480) = 150
- Client coords: 200 + 100 = 300, 150 + 50 = 200
- setNavigationGoal receives clientX=300, clientY=200
- setNavigationGoal converts back: (300-100) * (640/400) = 320 (correct!)

*** Benefits
- Voice-activated navigation now works correctly
- "find [object]" commands set goals to actual object positions
- Blind users can navigate to specific objects by voice
- Coordinate transformations are explicit and documented
- Future coordinate bugs easier to prevent and debug

** 19:00 - Fixed Direction Calculation X-Coordinate Inversion
Fixed critical bug where objects on the left were announced as being on the right due to X-coordinate inversion between canvas display and direction calculation.

*** Problem
Visual position and audio direction announcements were inverted:
- Bed visually on LEFT side of canvas
- Audio announces "bed approaching from RIGHT"
- Creates confusion for blind users about actual object positions
- Spatial awareness completely incorrect

*** Root Cause
Coordinate system mismatch between visual display and direction calculation:
- Canvas displays objects at their correct visual positions
- Backend YOLO detections provide bbox coordinates
- Frontend getObjectDirection() calculated direction from bbox
- BUT: X-coordinates were inverted compared to visual display
- Left side of frame had LOW X values but was being called "right"
- Right side of frame had HIGH X values but was being called "left"

*** Solution
Inverted normalizedX coordinate in getObjectDirection():
#+BEGIN_SRC javascript
// Before: normalizedX = centerX / imageWidth
// After: normalizedX = 1.0 - (centerX / imageWidth)

let normalizedX = centerX / imageWidth;
// CRITICAL FIX: Invert X coordinate to match visual display
normalizedX = 1.0 - normalizedX;
#+END_SRC

This flips the coordinate system so:
- Low X (left visually) -> normalizedX close to 1.0 -> "left"
- High X (right visually) -> normalizedX close to 0.0 -> "right"

** 18:15 - Fixed DeepSort Stale Track Announcements
Fixed critical issue where objects were being announced and drawn on canvas after they had disappeared from the scene, causing confusion for blind users.

*** Problem
Objects were being announced via audio AFTER they had already left the frame:
- User pans camera away from person
- Person disappears from view
- System still announces "person detected" several seconds later
- Creates confusing and inaccurate spatial awareness
- Particularly problematic for blind users relying on audio

*** Root Cause
Decoupled cleanup timing between canvas and announcements:
- Canvas cleanup (ui.js): Removed stale tracks with 3-second threshold BEFORE drawing
- Announcement cleanup (detection.js): Removed stale tracks at END of announceDetections() function
- This created a race condition:
  1. announceTrackingEvents() called FIRST (processes stale data)
  2. checkCollisionWarnings() called SECOND (processes stale data)
  3. Announcement queueing happens THIRD (processes stale data)
  4. Cleanup happens LAST (too late, announcements already queued)
- Result: Objects announced BEFORE their stale status was detected

*** Additional Issues
- Multiple tracking Maps persisted stale data:
  - previousTrackedObjects: No timestamp tracking
  - trackFirstSeen: Never proactively cleaned
  - trackLastMovement: Never proactively cleaned
  - collisionAlerts: Never proactively cleaned
- No unified stale threshold constant (hardcoded 3000ms in ui.js)
- Cleanup happened at different times in different modules

*** Solution: Proactive Cleanup Before Announcements
Restructured announcement pipeline to clean up stale tracks BEFORE processing:

**** 1. Added Timestamp Tracking
Modified previousTrackedObjects to include lastSeen timestamp:

    class_name: detection.class_name,
    movement: detection.movement,
    bbox: detection.bbox,
    collision: detection.collision,
    lastSeen: now  // CRITICAL: Track when object was last seen
});
#+END_SRC

**** 2. Centralized Stale Threshold
Added tracking.staleThreshold to TimingConfig.js:
- Value: 3000ms (3 seconds)
- Used consistently across canvas (ui.js) and announcements (detection.js)
- Single source of truth for stale object detection

**** 3. Reordered Cleanup Logic
Changed announceTrackingEvents() to clean BEFORE announcements:
#+BEGIN_SRC javascript
// Build current track IDs FIRST
const currentTrackIds = new Set();
detections.forEach(det => {
    if (det.confidence >= MIN_CONFIDENCE_THRESHOLD && det.track_id) {
        currentTrackIds.add(det.track_id);
    }

// CRITICAL FIX: Clean up stale tracks BEFORE announcements

** 10:28 - Fixed Object Tracking Misidentification
Fixed tracking system incorrectly treating new objects as the same object moving when camera pans quickly between objects of the same class.

*** Problem
When quickly moving the camera between two objects of the same class (e.g., two beds), the tracker would say the first object moved instead of recognizing a new object appeared.

*** Root Cause
- MAX_COSINE_DISTANCE = 0.4 was too lenient, allowing different objects to match
- MAX_TRACKER_AGE = 30 kept tracks alive too long after objects left the frame
- When panning to a new object, the old track would incorrectly match to it based on loose appearance matching

*** Changes
1. Reduced MAX_COSINE_DISTANCE from 0.4 to 0.25 for stricter appearance matching
2. Reduced MAX_TRACKER_AGE from 30 to 10 frames so tracks die faster when objects leave view
3. Reduced MIN_TRACK_INIT from 3 to 2 for faster new track initialization

*** Files Modified
- app/constants.py:37-41
  - Updated DeepSORT tracking parameters
  - Added inline comments explaining parameter changes

*** Technical Details
- DeepSORT uses MobileNet appearance descriptors and cosine distance for matching
- Lower cosine distance threshold = more strict appearance matching = fewer false matches
- Shorter tracker age = tracks expire faster = less chance of matching to wrong object
- Tracks now die within 10 frames (approximately 0.3 seconds at 30 fps) of losing detection

*** Benefits
- Correctly distinguishes between object movement and new objects
- Better handling of quick camera panning
- More accurate tracking for same-class objects in different locations
- Reduced false track associations

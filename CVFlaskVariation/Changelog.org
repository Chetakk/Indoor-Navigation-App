** [14:30] - BUGFIX: Fixed Left/Right Direction Inversion in Object Detection

Fixed critical bug where objects detected on the left side were announced as being on the right, and vice versa.

*** Problem Description
The audio guidance system was providing incorrect directional information to users. Objects physically located on the left side of the camera view were being announced as "right" and objects on the right were being announced as "left". This affected all directional features including:
1. Audio announcements for navigation assistance
2. Visual direction labels on the dashboard
3. Collision warning directions
4. Real-time detection panel display

*** Root Cause
The bug was located in =app/static/js/modules/detection.js= at line 229. The code incorrectly inverted the X-coordinate with =normalizedX = 1.0 - normalizedX= based on the false assumption that "Video/canvas coordinates have X inverted compared to YOLO detections."

In reality, YOLO detection coordinates use standard image coordinate systems where X=0 represents the left edge and X=width represents the right edge. No inversion was needed, and the inversion was causing the directional calculations to be backwards.

*** Changes Made
1. Removed the incorrect coordinate inversion in =app/static/js/modules/detection.js= (line 229)
   - Deleted: =normalizedX = 1.0 - normalizedX;=
   - Changed =normalizedX= from =let= to =const= since it no longer needs to be reassigned
2. Updated code comments to clarify that no inversion is needed
3. Updated debug log message to remove "AFTER inversion" text

*** Impact
- All directional announcements now correctly match the physical location of objects
- Left-side objects are properly announced as "left"
- Right-side objects are properly announced as "right"
- Collision warnings now provide accurate directional guidance
- Visual overlays show correct direction labels

*** Files Changed
- =app/static/js/modules/detection.js= - Lines 224-231

*** Technical Notes
YOLO bounding boxes use standard image coordinates:
- (x1, y1) = top-left corner
- (x2, y2) = bottom-right corner
- X increases from left to right (0 to width)
- Y increases from top to bottom (0 to height)

The video element displays these coordinates correctly without any mirroring or transformation, so no coordinate system conversion is needed.

** [10:15] - MONITORING: Added Browser Throttling Detection for Frame Uploads

Added monitoring and diagnostics to detect when browser throttles frame upload timers, which can cause dashboard streaming to stop.

*** Problem Description
After showing the same scene for several seconds, the client would completely stop sending frame upload requests to the server. This was not related to detection errors but appeared to be a browser behavior issue.

*** Root Cause Analysis
Mobile browsers (especially on iOS/Android) aggressively throttle or stop setInterval timers when:
1. The tab goes to background or becomes hidden
2. The screen locks or device enters power-saving mode
3. Browser detects the page is inactive for battery optimization

The frame upload uses setInterval at 33ms (30 FPS), which is particularly susceptible to throttling.

*** Changes Made
1. Added throttling detection to frame upload loop in =app/static/js/modules/camera.js=
   - Track time between frame uploads (expected: 33ms)
   - Warn if interval exceeds 100ms (indicates browser throttling)
   - Added =lastFrameUploadTime= and =frameUploadStallWarningShown= state variables (lines 37-38)

2. Implemented Page Visibility API monitoring (lines 788-815)
   - Detect when page becomes hidden/visible
   - Log warnings when page is hidden (browser will throttle timers)
   - Reset throttle warning flag when page becomes visible again
   - Check for Wake Lock API support to prevent screen sleep

3. Enhanced error logging in frame upload
   - Changed from silent error handling to occasional logging (5% sample rate)
   - Helps identify upload failures without console spam

*** Impact
- Users will now see console warnings when browser starts throttling timers
- Clear indication that page needs to stay active for continuous operation
- Helps diagnose frame upload stalls vs. actual code errors
- Wake Lock API support detection for future enhancements

*** Files Changed
- =app/static/js/modules/camera.js= - Lines 37-38, 740-750, 766-770, 788-815

*** Technical Notes
The 30 FPS frame upload rate is necessary for smooth dashboard viewing but makes the system susceptible to browser power management. Future improvements could include:
1. Implementing Wake Lock API to prevent screen sleep
2. Using requestAnimationFrame instead of setInterval for better throttling resistance
3. Implementing WebSocket for push-based frame delivery
4. Adaptive frame rate based on visibility state

*** Recommendations for Users
- Keep the browser tab active (foreground) during operation
- Keep screen on to prevent device sleep
- Use "Keep Screen On" browser extensions if available
- Consider using desktop browsers for dashboard monitoring

** [09:42] - BUGFIX: Fixed Collision Detection AttributeError with None Values

Fixed critical AttributeError crash occurring when collision_warnings tried to access .get() on None collision objects.

*** Root Cause
When tracking was disabled or objects were untracked, the collision field was set to None. The collision warning filter at line 383 used =obj.get('collision', {}).get('collision_risk', False)= which would fail when collision was None instead of a dict, because None.get() would try to call get() on NoneType.

*** Changes Made
1. Fixed collision_warnings list comprehension (lines 383-387)
   - Now properly checks: =obj.get('collision') is not None=
   - Then verifies: =isinstance(obj.get('collision'), dict)=
   - Only then accesses: =obj.get('collision').get('collision_risk', False)=
2. Added missing 'collision': None key to raw detection objects (line 368)
   - Ensures consistency across all object dictionaries
   - Previously this key was missing when tracking was disabled

*** Error Details
- Error: ='NoneType' object has no attribute 'get'=
- Location: =app/routes/detection.py:383= in collision_warnings list comprehension
- Traceback showed: =obj.get('collision', {}).get('collision_risk', False)=
- Impact: Detection pipeline crashed, UI showed no detections

*** Files Changed
- =app/routes/detection.py= - Lines 368, 383-387

*** Technical Notes
The issue occurred because .get('collision', {}) returned None (the actual value) rather than the default {}, since the key existed but had None as its value. The fix properly distinguishes between missing keys and None values.

** [09:30] - BUGFIX: Corrected Left/Right Object Side Detection

Fixed critical bug where object position announcements were reversed (objects on left reported as right and vice versa).

*** Root Cause
The cross product calculation in =app/services/pathfinder.py= had inverted logic for determining left vs right side positioning.

*** Changes Made

   - Changed: =cross > 0= now correctly maps to "left"
   - Changed: =cross < 0= now correctly maps to "right"

   - Applied same correction to obstacle side detection
   - Ensures warnings like "person on left" are accurate

*** Technical Details
- Cross product =np.cross(goal_direction, safe_direction)= returns positive when safe_direction is counter-clockwise (left) from goal_direction in standard image coordinates
- Previous logic had the sign interpretation backwards
- Fix applies to both navigation directions ("turn left") and obstacle warnings ("person on left")

** 19:15:00 - VISION-BASED POSITION TRACKING: Visual Odometry for Navigation
Replaced time-based movement simulation with vision-based position tracking using object detections and depth data.

*** Implementation
**** Visual Odometry Algorithm (estimate_camera_movement)
Uses tracked objects between frames to estimate camera movement:

1. *Object Matching*: Match objects across frames using track_id
2. *Distance Analysis*: Compare real-world distances (from depth estimation)
   - distance_change = prev_distance - curr_distance
   - Negative = moving toward object, Positive = moving away
3. *Movement Vector Calculation*:
   - Direction: From camera to object center in image
   - Magnitude: distance_change * 100 (pixels per meter)
4. *Weighted Average*: Combine estimates from multiple objects
   - Weight by distance_confidence from depth estimator
   - Require at least 2 matched objects for reliability
5. *Confidence Score*: Average confidence from all matched objects

**** Integration with Navigation
- Primary: Vision-based tracking (confidence > 0.3)
- Fallback: Time-based simulation (confidence <= 0.3 or no matches)
- Session storage: Previous detections for frame-to-frame comparison
- Automatic position updates based on object distance changes

*** Technical Details
*Requirements for Vision-Based Tracking*:
- Minimum 2 tracked objects with track_id
- Distance confidence > 0.3 for both frames
- Distance change > 0.1 meters (ignore noise)
- Valid bbox coordinates for object centers

*Advantages Over Time-Based*:
- No assumption user follows directions
- Works with any camera movement (forward, backward, sideways, turning)
- Accounts for real depth changes from depth estimator
- More accurate as user approaches/leaves objects

*Confidence Thresholds*:
- >0.3: Use vision-based estimate
- <=0.3: Fallback to time-based simulation
- 0.0: Not enough matched objects (< 2)

** 00:25 - Fixed Voice-Activated Object Navigation Coordinate Bug
Fixed critical bug where voice-activated "find [object]" commands were setting navigation goals to incorrect locations due to coordinate transformation errors.

*** Problem
When using voice commands like "find bench" or "find door", the navigation system would set the goal to completely wrong locations on the canvas:
- Objects detected correctly with proper bounding boxes
- Voice command found the correct object
- But navigation goal was set to wrong position
- User would be directed to empty space instead of the object
- Made voice-activated navigation completely unreliable

*** Root Cause
Incorrect coordinate transformation in handleFindCommand() (main.js:224-227):
- Started with centerX, centerY in VIDEO coordinate space (e.g., 320, 240 for 640x480 video)
- Incorrectly scaled by canvas.width / videoWidth (inverse of what was needed)
- Passed result as clientX, clientY without accounting for canvas position
- setNavigationGoal() expected CLIENT coordinates (browser viewport space)
- setNavigationGoal() then converted client -> video (assumed double transformation)
- Result: goal position was completely wrong

*** Coordinate Space Confusion
Three coordinate spaces were conflated:
1. Video coordinates: [0, videoWidth] x [0, videoHeight] (e.g., 640x480)
2. Canvas coordinates: [0, canvas.width] x [0, canvas.height] (e.g., 400x300 if scaled)
3. Client coordinates: Browser viewport position (e.g., 100-500 if canvas at left=100)

Old code:
#+BEGIN_SRC javascript
// WRONG: Started in video space, scaled incorrectly, treated as client space
const syntheticEvent = {
    clientX: centerX * (detectionCanvas.width / (videoElement.videoWidth || 640)),
    clientY: centerY * (detectionCanvas.height / (videoElement.videoHeight || 480))
};
#+END_SRC

This produced coordinates in CANVAS space (0-canvas.width), but labeled them as client coordinates, causing setNavigationGoal() to misinterpret them.

*** Solution
Implemented proper three-stage coordinate transformation:
1. Start with video coordinates (from bbox)
2. Scale to canvas coordinates (multiply by canvas/video ratio)
3. Offset to client coordinates (add canvas rect.left and rect.top)

New code:
#+BEGIN_SRC javascript
// CORRECT: Proper transformation through all three coordinate spaces
const rect = detectionCanvas.getBoundingClientRect();
const scaleX = detectionCanvas.width / (videoElement.videoWidth || 640);
const scaleY = detectionCanvas.height / (videoElement.videoHeight || 480);

// Transform: video coords -> canvas coords -> client coords
const canvasX = centerX * scaleX;
const canvasY = centerY * scaleY;
const clientX = canvasX + rect.left;
const clientY = canvasY + rect.top;

const syntheticEvent = {
    clientX: clientX,
    clientY: clientY
};
#+END_SRC

*** Files Modified
- app/static/js/main.js:214-240
  - Fixed coordinate transformation in handleFindCommand()
  - Added proper video -> canvas -> client transformation
  - Added inline comments explaining coordinate spaces
  - Now correctly calculates clientX and clientY for setNavigationGoal()

*** Technical Details
Transformation mathematics:
- Video to Canvas: canvasCoord = videoCoord * (canvasSize / videoSize)
- Canvas to Client: clientCoord = canvasCoord + canvasOffset
- Combined: clientCoord = videoCoord * (canvasSize / videoSize) + canvasOffset

Example (object at video center on 640x480 video, canvas 400x300 at position 100,50):
- Video coords: centerX=320, centerY=240
- Canvas coords: 320 * (400/640) = 200, 240 * (300/480) = 150
- Client coords: 200 + 100 = 300, 150 + 50 = 200
- setNavigationGoal receives clientX=300, clientY=200
- setNavigationGoal converts back: (300-100) * (640/400) = 320 (correct!)

- Creates confusion for blind users about actual object positions

*** Root Cause
Coordinate system mismatch between visual display and direction calculation:
- Canvas displays objects at their correct visual positions
- Backend YOLO detections provide bbox coordinates
- Frontend getObjectDirection() calculated direction from bbox
- BUT: X-coordinates were inverted compared to visual display
- Left side of frame had LOW X values but was being called "right"
- Right side of frame had HIGH X values but was being called "left"

*** Solution
Inverted normalizedX coordinate in getObjectDirection():
#+BEGIN_SRC javascript
// Before: normalizedX = centerX / imageWidth
// After: normalizedX = 1.0 - (centerX / imageWidth)

// CRITICAL FIX: Invert X coordinate to match visual display
normalizedX = 1.0 - normalizedX;
#+END_SRC

This flips the coordinate system so:
- Low X (left visually) -> normalizedX close to 1.0 -> "left"
- High X (right visually) -> normalizedX close to 0.0 -> "right"

- latestRequestId: ID of the most recent request sent
- thisRequestId: ID assigned to current request
- Check: thisRequestId === latestRequestId before processing

**** Stale Response Detection
Two checkpoints to ignore stale responses:
1. After response received (before JSON parsing)
2. After JSON parsing (before drawing on canvas)

This prevents race conditions where multiple async operations complete.

** 18:39 - Replaced A* Pathfinding with Reactive Navigation System

*** Problem

- A* assumes static environments (doesn't handle moving people, vehicles)
- A* requires complete knowledge of environment (only sees current camera frame)
- A* calculates path once then follows it (but scene changes every frame)

- A* designed for: static maps (buildings, walls), complete environment knowledge, one-time path calculation
- Our system has: dynamic obstacles (people walking), partial knowledge (camera view only), constantly changing scene
- Misalignment between algorithm assumptions and reality

*** Solution: Reactive Local Navigation

- No long-term path planning (adapts every frame)

** 10:28 - Fixed Object Tracking Misidentification
Fixed tracking system incorrectly treating new objects as the same object moving when camera pans quickly between objects of the same class.

*** Problem
When quickly moving the camera between two objects of the same class (e.g., two beds), the tracker would say the first object moved instead of recognizing a new object appeared.

*** Root Cause
- MAX_COSINE_DISTANCE = 0.4 was too lenient, allowing different objects to match
- MAX_TRACKER_AGE = 30 kept tracks alive too long after objects left the frame
- When panning to a new object, the old track would incorrectly match to it based on loose appearance matching

*** Changes
1. Reduced MAX_COSINE_DISTANCE from 0.4 to 0.25 for stricter appearance matching
2. Reduced MAX_TRACKER_AGE from 30 to 10 frames so tracks die faster when objects leave view
3. Reduced MIN_TRACK_INIT from 3 to 2 for faster new track initialization

*** Files Modified
- app/constants.py:37-41
  - Updated DeepSORT tracking parameters
  - Added inline comments explaining parameter changes

*** Technical Details
- DeepSORT uses MobileNet appearance descriptors and cosine distance for matching
- Lower cosine distance threshold = more strict appearance matching = fewer false matches
- Shorter tracker age = tracks expire faster = less chance of matching to wrong object
- Tracks now die within 10 frames (approximately 0.3 seconds at 30 fps) of losing detection

*** Benefits
- Correctly distinguishes between object movement and new objects
- Better handling of quick camera panning
- More accurate tracking for same-class objects in different locations
- Reduced false track associations
